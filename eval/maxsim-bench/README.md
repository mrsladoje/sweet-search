# MaxSim kernel benchmark

Times sweet-search's native MaxSim kernel (`crates/sweet-search-native/src/maxsim/`) on
real calls captured from its production search path, against every CPU MaxSim
implementation we could find, each in its fastest configuration, on Apple Silicon and
x86. Published numbers come only from **held-out** data.

- Results: [RESULTS.md](RESULTS.md) (generated by `summarize.py`; raw per-call results for
  every arm, round and call in `published/results-2026-10-13.tar.zst`).
- Kernel design: [docs/MAXSIM_OPTIMIZATION.md](../../docs/MAXSIM_OPTIMIZATION.md).

## What is compared

MaxSim score of a query (Q token vectors) against each candidate document (D token
vectors): for each query token the best cosine over the document's tokens, averaged
over the query tokens. sweet-search clamps a negative best to 0 (`max(0, ·)`).

| arm | what runs | input it gets |
|---|---|---|
| **sweet kernel** (`ours`) | the production kernel source, compiled unchanged into a C ABI (`capi/`), called from Python | the index's storage: int4 per token (nibble-packed), per-token min / scale, stored norms; raw query |
| sweet production path (`node:production`) | what the rerank stage calls: `nativeMaxSimPacked` in `core/infrastructure/simd-distance.js` (JS packing + N-API + kernel) | docs as loaded from an index segment (one slab per segment) |
| previous production path (`node:legacy`) | the code before this change: one JS object per candidate into the old addon | same |
| sweet fallback tiers (`node:wasm`, `node:js`) | the WASM SIMD tier and the plain-JS tier (used when the native addon is missing) | same |
| [maxsim-cpu](https://github.com/mixedbread-ai/maxsim-cpu) 0.1.0 | `maxsim_scores_variable` (ragged list) or `maxsim_scores` (padded 3D) | **its best case:** f32 docs already dequantized and divided by their norms, L2-normalized query, contiguous, prepared outside the timer |
| NumPy (Accelerate on macOS, OpenBLAS on Linux) | one GEMM over all docs concatenated, then `np.maximum.reduceat` per doc (both layouts) | same best case |
| PyTorch CPU | padded `bmm` / flat matmul (fast-plaid, pylate-rs shape); PyLate's `colbert_scores`; colbert-ai's packed GEMM + its C++ `segmented_maxsim` ([vendored](third_party/)); `torch.segment_reduce` | same best case |
| [NumKong](https://github.com/ashvardanian/NumKong) 7.8.5 | `maxsim_packed`, docs pre-packed (bf16 / f16 / f32), one call per doc on a thread pool | same best case; **approximate** (int8 screening, then refinement) |
| NumPy / maxsim-cpu **+ int4** | as above, but given the same int4 storage as sweet and dequantizing it inside the timed call | the index's storage |

Every rival runs in several configurations (API variant, thread count: default, the
performance cores, 1; dtype). The tables show each library at its **fastest**
configuration for each workload, chosen on the very calls reported (which can only
favour it), plus a single-thread table. The configurations were shortlisted on dev
data (`results/x86-dev-shortlist/`); adding more can only help the rivals.

**Correctness of every arm** is checked on every call against a float64 reference of
the same formula (`bench.py: reference`): max absolute error and top-1 agreement are in
every table. Findings: maxsim-cpu's x86 wheel returns wrong scores (up to 1e38 and inf)
for queries over 32 tokens once a doc reaches 64 tokens
([mixedbread-ai/maxsim-cpu#1](https://github.com/mixedbread-ai/maxsim-cpu/issues/1);
reproduced on the box), so on x86 it is run in 32-token query chunks, whose sums add up
exactly; NumKong is approximate (max error ~0.1, top-1 agreement ~92% on these calls).

## Data (held-out only in RESULTS.md)

| set | source | calls |
|---|---|---|
| agent-ho | every unique `ss-search` / `ss-semantic` / `ss-find` call agents made on the **held-out** questions of the retrieval bench (`core/prompt-optimization/data/final-run/questions-heldout.json`), replayed on the 11 `eval/repos/r3-*` repos through the production search path (`extract-calls.py --heldout`, `run-capture.sh`) | 2,004 |
| gcsn-ho | GenCodeSearchNet **held-out** split (2,400 queries, `eval/run_benchmark.js --split=heldout`) | 2,385 |
| sweep-ho | size sweep built only from real held-out embeddings (`make_sweep.py`, seed 42): 4,315 real queries cut to 8 / 32 / 64 tokens × pools of 1 to 4,096 real docs × natural length or real docs cut to 32 / 128 / 512 tokens; 84 cells | 2,913 |
| agent-dev, gcsn-dev, sweep-dev | the same from the **dev** split, for development and the rival shortlist only | 655, 3,582, 207 |

Dev and held-out queries never overlap. The kernel was developed on dev data only;
held-out sets were scored only at milestones, in aggregate (CLAUDE.md, Benchmark
Methodology). All captured calls use the production format (int4 per token, dim 128).
`make_sweep.py` writes byte-identical sweeps on both machines (SHA-256 of the dev and
held-out sweeps checked on both).

## Method

- **One arm per process.** Rival libraries keep their worker threads spinning after a
  call (OpenBLAS up to ~100 ms, OpenMP, rayon; our pool for 0.2 ms). In one process
  they would slow the next arm, so `run_matrix.py` runs each arm alone.
- **Rounds.** Two rounds over all arms, the second in reversed order; per call the
  median over rounds. Slow drift (heat, background load) hits every arm alike.
- **Idle gate.** Before every arm, `run_matrix.py --max-busy` waits until machine CPU
  use (sampled over 1 s) is low; `wait_quiet.py` gates a whole matrix (macOS: on AC power).
- **Per call:** one untimed warm-up, then 5 timed calls (3 when cold); latency = median.
- **Warm** = calls back to back. **Cold** = 5 ms of busy main thread before every call,
  so worker pools have parked, as in a search where scoring follows other work.
- **Ratios** are geometric means over calls of (other / sweet), with 95% bootstrap
  intervals (10,000 resamples, seed 42); "sweet faster on" is the share of calls.
- Inputs for the rivals are built outside the timer; sweet's input is the stored int4 format.

## Correctness gate for kernel changes

`parity.mjs` compares two builds score by score (`Object.is` on every f64): seeded
fixtures that hit every kernel branch (odd dims, dims not a multiple of 4/8/16/32,
tile edges, >64 query tokens, empty docs, zero scales, NaN / huge / tiny inputs,
1,000-doc pools, malformed descriptors) and every replayed call, through the object
and the packed entry points, int4 and int8. Every change of this pass is bit-identical
to the previous kernel on both platforms (0 diffs on fixtures, dev, and held-out:
574,128 held-out scores on x86). End to end, re-capturing GCSN dev and agent dev
through the new production path gives the same score for every call (GCSN dev MRR@10
87.00% before and after). One side finding: in ~6% of agent calls the rerank stage
receives the same candidates in a different order from run to run; two runs of the
old code show the same (42 of 655 vs 40 old-vs-new), so it predates this change.

## Reproduce

```bash
cd eval/maxsim-bench
uv venv --python 3.12 venv && VIRTUAL_ENV=$PWD/venv uv pip install maxsim-cpu numpy torch numkong threadpoolctl ninja
(cd capi && cargo build --release)                  # the C ABI over the kernel source
O=~/.ss-eval/maxsim-replay

# capture (production search path, hooked), dev and held-out
python3 extract-calls.py $O/agent-ho/calls.json --heldout
./run-capture.sh $O/agent-ho composer dgraph drogon grdb jj ocelot okhttp sequel tortoise-orm typedoc zipkin
SS_MAXSIM_DUMP=$O/gcsn-ho/gcsn NODE_OPTIONS="--import $PWD/hook.mjs" \
  node ../run_benchmark.js --dataset=gencodesearchnet --split=heldout --profile=full --sqlite-fast --concurrency=1 --skip-index
venv/bin/python -I make_sweep.py $O/sweep-ho $O/agent-ho $O/gcsn-ho

# gate a kernel change, then the matrix and the tables
node parity.mjs old.node new.node $O/agent-dev $O/gcsn-dev
LEGACY_ADDON=<previous production .node> ./final.sh <platform> $O
venv/bin/python summarize.py results/<platform> --md RESULTS-<platform>.md
```

`ab.mjs` (two builds on replayed calls, same process), `synth.mjs` (synthetic shapes,
idle-gap modes) and `bench-ours.mjs` remain for kernel work.
