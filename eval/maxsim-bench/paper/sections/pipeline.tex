\section{Share of MaxSim in a search}
\label{sec:pipeline}

In the search path of sweet-search, MaxSim took a median of \nm{pipe.maxsim.med}\% of the time of a held-out agent search call.
Microseconds in the kernel matter only if MaxSim is a visible part of a search, so we timed the stages of the production search path of sweet-search.
We replayed the \nm{pipe.calls.all} held-out agent search calls on the M3 Max, with the production configuration and a CPU query encoder (ONNX Runtime).
\nm{pipe.calls} of these calls ran MaxSim; Table~\ref{tab:pipeline} reports them.
Each call ran once to warm up and then \nm{pipe.passes} times with timers; we cleared the query embedding cache before each timed pass, so the encoder ran as for a new query.
The pass with the median total time gives the split of the call.
This measurement ran after the freeze, on the frozen code, and changed no engine code: the timers come from a preloaded module.
We report aggregates only.

The stages are these.
\emph{Query encoding} is the dense query embedding and the late-interaction query tokens, from the engine's own counters.
\emph{Candidate fetch} is the first-stage retrieval, minus the encoder and late-interaction time inside it.
\emph{int4 load} is the late-interaction scoring minus the kernel: the lookup in the in-memory int4 store, grouping and packing.
\emph{MaxSim} is the native kernel call.
\emph{The rest} is routing, post-processing and output shaping.
The fetch of one tool, ss-semantic, has no separate timer, so it counts as the rest.

Candidate fetch and query encoding took most of the time, with medians of \nm{pipe.fetch.med}\% and \nm{pipe.encoding.med}\% of a call.
The kernel took a median of \nm{pipe.maxsim.ms}\,ms, \nm{pipe.maxsim.med}\% of a call, and \nm{pipe.maxsim.p90}\% at the p90.
The int4 load took about the same share, \nm{pipe.int4.med}\%.
So on this path, a kernel with zero cost would shorten the median call by less than 1\%.
This is not an end-to-end speed-up claim, and it does not show that a slower kernel would be acceptable elsewhere.
Kernel time matters more with many more candidates per call (Section~\ref{sec:sweep}), with many callers (Section~\ref{sec:conc}), or with a faster encoder and fetch.
We did not measure such pipelines.

The indexes differ from production in one step.
The bench repositories hold indexes in an older file format, which the frozen engine does not read.
We converted copies of them to the current format with the same graph, codes and int8 rows, without re-embedding.
The converter does not build the file of full-precision vectors, so the final full-vector rescore of the first-stage candidates was off.
That step is part of candidate fetch in production, so fetch takes a larger share there and MaxSim a smaller one.
