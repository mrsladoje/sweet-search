\section{Introduction}
\label{sec:intro}

Late-interaction retrieval models such as ColBERT~\cite{khattab2020colbert,santhanam2022colbertv2} keep one vector per token.
They score a query against a document with MaxSim.
Each query token takes its best similarity over the document tokens, and the score is the mean of these maxima.
Many systems use MaxSim as a reranking stage.
A first stage (BM25 or a single-vector index) returns tens or hundreds of candidates, and MaxSim orders them.

Rerank calls are small.
In the coding-agent workload of this paper, the median call has \nm{wl.agent-ho.q50} query tokens and \nm{wl.agent-ho.pool50} candidates of about \nm{wl.agent-ho.dt50} tokens each (Section~\ref{sec:workload}).
At this size a call takes tens of microseconds, while common tools are built for large matrix products.
Which CPU implementation is fastest for such calls, at what quality and under which conditions, is an empirical question.
A natural guess is that fixed costs, such as library dispatch and thread wake-up, decide it; Section~\ref{sec:floor} probes this guess with the smallest possible call.
Earlier work timed CPU MaxSim libraries as baselines for faster approximate methods~\cite{pony2026colbandit}, or timed a single library~\cite{clavie2025maxsimcpu}.
We found no public benchmark that compares CPU MaxSim implementations on captured rerank calls and checks each implementation against its own scoring rule.

This paper makes four contributions.
\begin{enumerate}
\item \textbf{A benchmark} (\benchname, for Late-Interaction Reranking Kernels). It has a replay format for rerank calls, four workload families, adapters for eight implementations, and a timing record for every repetition of every call.
\item \textbf{Scoring contracts.} The tested libraries compute different scores. They differ in normalization, in the place of an epsilon, in a $\max(0,\cdot)$ clamp, and in padding. On float vectors of unit length the rules nearly agree; on int4 tokens they diverge, because they divide by different norms. We define each rule once, compute a float64 reference per rule, and check every implementation against the reference of its own rule (Section~\ref{sec:contracts}).
\item \textbf{A measurement protocol.} The code, the rival configurations, the repetition count, the quality margin and the primary tests were frozen before any held-out run (Section~\ref{sec:method}). The tables of this paper come from analysis code written after the freeze; Appendix~\ref{app:deviations} lists each difference from the frozen scripts.
\item \textbf{Results on five CPUs} (Granite Rapids, Zen~5, Graviton4, Apple M3 Max, and Zen~3). We measure speed under warm, busy-gap, one-thread and parallel-caller conditions, memory per stored token, and quality per latency budget. Section~\ref{sec:losses} lists every condition in which a rival was faster.
\end{enumerate}

One of the implementations is an int4 kernel from the open-source code-search engine sweet-search (\sweet below).
It is careful engineering, not a new algorithm (Section~\ref{sec:kernel}).
The authors of this paper also wrote that kernel.
For this reason, the rival configurations come from a shortlist that was chosen on development data and frozen, and the claims follow rules that were fixed before the held-out runs.

\paragraph{What we claim.}
Our first claim concerns the benchmark itself.
MaxSim implementations compute different scores, so a fair comparison must check each one against a reference of its own rule.
These checks found two new defects in other libraries and confirmed a known one (Section~\ref{sec:correctness}).
Our second claim concerns speed.
On the tested CPUs, with warm calls, \sweet reduced scoring latency for the captured agent and code-search rerank calls, relative to every frozen exact rival configuration with float32 inputs.
It does so with exhaustive scoring over stored int4 representations and measured floating-point error.
This claim does not hold in every condition, and Section~\ref{sec:losses} lists where it fails.
Our third claim concerns quality: the int4 scoring rule was non-inferior to float32 for ColBERTv2 in the pre-registered test, and it lost quality for answerai-colbert-small (Section~\ref{sec:quality}).
We do not claim the fastest MaxSim in general, any end-to-end search speed-up, or any GPU result.
We also do not claim why \sweet is faster, because we did not decompose the cost of a call (Section~\ref{sec:limits}).
