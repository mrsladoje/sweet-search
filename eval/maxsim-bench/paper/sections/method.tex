\subsection{Machines}

Table~\ref{tab:machines} lists the five CPUs.
The three cloud types are AWS EC2 on-demand instances in us-east-1.
Each held-out set ran whole on one instance; four instances per type shared the sets.
A fifth instance per type (the replica) repeated the agent and GCSN sets.
The EPYC is a dedicated-vCPU virtual machine at Hetzner. The Linux machines report no frequency governor; the hypervisor controls frequency.
No arm was pinned to a core.
The Linux machines used Python~3.12.3, NumPy~2.5.4 on OpenBLAS~0.3.34, PyTorch~2.14.1 (CPU build), Node.js~24.18.0 and Rust~1.97.1.
One AMD variant used NumPy on BLIS~2.0, and NextPlaid links OpenBLAS~0.3.26.
The Mac used Python~3.12.13 and Apple Accelerate.
Lock files pin every Python and Rust dependency.

\subsection{Arms and the frozen shortlist}

An \emph{arm} is one implementation in one configuration.
Each library ran in several configurations: API variant, input type and thread budget.
The input types are float32, bfloat16 and float16.
For NumPy and maxsim-cpu there is also ``int4-self'': the rival receives the int4 storage and decodes it with NumPy inside its timed call.
The thread budgets are the library default (all logical CPUs), the physical or performance cores, and one; the default was a candidate for every library.
Appendix~\ref{app:terms} names every variant.

On the development sets, a script chose, per machine, library, input type and workload family, the two configurations with the smallest total time and the fastest one-thread configuration.
The BEIR family has no development data; for it the script used the development sweep cells with 32 query tokens, the BEIR query length.
This \emph{shortlist} was frozen with everything else.
Each table row shows, per library and input type, the faster of its two frozen configurations on the reported calls.
This choice inside the frozen set can only favour the rival.
The released tables also give each frozen configuration and the fastest configuration that ran, frozen or not (``post hoc'').

PyLate's scoring is re-implemented line by line from its CPU path (\texttt{colbert\_scores} 1.6.0), and colbert-ai's packed scoring uses its vendored C++ file; no PyLate configuration was shortlisted on any CPU, and colbert-ai's packed scoring appears as one of PyTorch's configurations.
We gave the rivals their best case.
Their inputs are the int4 storage decoded to float32, normalized, cast and packed outside the timer; the memory measurement counts these copies.
So the ``float32'' rivals score the same int4 data as \sweet; Section~\ref{sec:budget} adds float32 storage as a separate line.
NumKong has no batch interface, so besides its Python interface we looped its C kernel over the documents in Rust (``native'' arms).
We looped NextPlaid's scorer the same way, with one thread and with a thread pool.
maxsim-cpu's x86 build returns wrong scores for queries over 32 tokens once a document has 64 tokens (Section~\ref{sec:correctness}).
On x86 we therefore call it in 32-token query chunks, whose sums are exact.
Intel MKL NumPy did not install from Intel's package index and is missing.
maxsim-cpu has no Linux AArch64 wheel and is missing on Graviton4.

\subsection{Timing}

Each arm runs in its own process.
Rival thread pools keep spinning after a call (OpenBLAS for up to about 100\,ms) and would slow the next arm.
Before each arm, the runner waits until machine CPU use, sampled over one second, is below 10\% (15\% on the Mac).
Per call, one untimed warm-up precedes the timed repetitions.
\begin{description}
\item[Warm:] calls back to back; 5 timed repetitions per call.
\item[Pool-parked (5\,ms busy gap):] the main thread spins for 5\,ms before every call, so worker pools that park after a short wait (\sweet: 200\,$\mu$s) have parked, while pools that spin longer (OpenBLAS) may still be awake; 3 timed repetitions. This mode does \emph{not} test cold caches or process start.
\item[One thread:] the one-thread configurations, warm.
\item[Parallel callers:] see Section~\ref{sec:conc}.
\end{description}
Every arm of the matrix runs (warm, busy gap, one thread) runs $R = 5$ process repetitions $\times$ 2 rounds; the second round runs the arms in reversed order. The parallel-caller runs follow their own scheme (Section~\ref{sec:conc}).
A call's latency is the median of its 10 run medians.
We keep every individual timing.
``Per-request p95/p99'' pools all of them and is the only tail statistic we report.

\paragraph{Ratios and uncertainty.}
A speed ratio is the geometric mean over calls of (rival time / \sweet time); above 1 means \sweet is faster.
We report two uncertainty numbers apart.
The \emph{workload interval} is a 95\% cluster-bootstrap interval (10,000 resamples, seed 42).
It resamples repositories for agent calls (11 clusters), queries for GCSN and BEIR calls, and calls for sweep cells.
The 11 repositories hold \nm{agent.repos.min} to \nm{agent.repos.max} calls each, and five of them hold \nm{agent.repos.top5}\% of all calls, so the effective number of clusters is about \nm{agent.repos.eff}.
With so few clusters this interval can be too narrow, so Appendix~\ref{app:robust} also gives the per-repository range and the leave-one-repository-out range.
As a second number we report a \emph{leave-one-process-out sensitivity}: the range of the ratio when one of the five process repetitions is left out, with the same median-of-runs estimator. It shows how much one process changes the result; it is not a calibrated interval.
The replica instance adds an instance-to-instance spread (Section~\ref{sec:spread}).
The leave-one-process-out range is narrow, because each estimate shares 8 of 10 runs; the ratio fell outside the range of the five single-process estimates (each the mean of its 2 rounds) in \nm{spread.outside.n} of \nm{spread.rows.n} warm rows, because the median of 10 runs drops slow outlier runs that a mean of 2 keeps.
We call a rival \emph{faster} only if its whole workload interval, all five leave-one-process-out estimates and all five single-process estimates are below 1. This rule was set after the freeze, during the analysis. Sweep and loss counts that use only the point estimate say ``ratio below 1''.
This rule is descriptive; we do not correct it for the many comparisons.
Beside the geometric mean we computed the total-time ratio (sum of rival times over sum of \sweet times), which weights large calls more.
For no exact rival with float32 inputs does it fall on the other side of 1; for \nm{totalflip.n} BEIR rows with other input types it does (Section~\ref{sec:losses}).

\paragraph{Noise check and $R$.}
On development data, an A/A run (the same build as two arms, 5 process repetitions) gave per machine the coefficient of variation $cv$ of the set-level geometric mean.
The noise band $n = \max(1\%, 2\,cv)$ was: Intel \nm{noise.intel}\%, AMD \nm{noise.amd}\%, Graviton4 \nm{noise.arm}\%, M3 Max \nm{noise.m3max}\%, EPYC \nm{noise.epyc}\%.
The rule $R = \operatorname{clamp}(\lceil (cv/0.01)^2\rceil, 3, 8)$ gave 3 or 4.
We used $R = \max(5, \text{noise rule}) = 5$ on all machines; an early plan with $R = 3$ was corrected before any held-out run.

\subsection{Correctness checks}

In every run, the harness checks the scores of the untimed warm-up call of every call.
So each call is checked ten times per arm, once per run.
The timed repetitions repeat the same computation on the same inputs and are not checked again.
Per arm we report the largest absolute error against reference (a) of its own contract, the input-rounding effect, and the agreement of its top-ranked document with the contract-S reference.
For the BEIR sets every arm stores all its scores, so each implementation gets its own quality curve.

\subsection{Development, freeze and held-out runs}
\label{sec:freeze}

All tuning used development data only.
The last kernel change (the AVX-512 block) was kept on development data under a pre-set rule: at least 3\% faster and above the noise band in two rounds on the target machine, no slowdown above the band elsewhere, and bit-identical scores.
A second candidate (a thread-count rule by call size) failed that rule and was dropped.
The rivals received configuration selection, not code changes.

Then we froze, in one file, the code, every adapter, the shortlists, the analysis scripts, the dataset definitions, the contracts, $R$, the quality margin $\delta$, the four primary quality tests, the parallel-caller rates, and a rule for a stronger claim.
Three commits define the freeze: \texttt{a4317ba9} (the frozen code), \texttt{ea84951f} (the freeze file re-made after a replica naming fix; the held-out bundle came from it) and \texttt{daf54122} (a memory fix in the parallel-caller harness with its new freeze entry, applied to every machine before any reached a parallel-caller group).
A script checks the SHA-256 of every frozen file before use.
The freeze file hashes the agent and GCSN sets directly; the BEIR and sweep sets are fixed by their build scripts, seed and release manifest.

\paragraph{Held-out discipline.}
We read held-out results only as aggregates.
No per-query or per-call held-out row was printed or inspected, and nothing was tuned after a held-out result was seen.
The tables come from analysis code written after the freeze (Appendix~\ref{app:deviations} lists each difference from the frozen scripts).
