\section{Limits}\label{sec:limits}

\paragraph{Sizes and dimensions.} The sets hold 7k to 1M vectors. We make no claim beyond 1M vectors. All vectors have 768 dimensions; our codes use the first 512. Other dimensions, and models
whose leading dimensions carry less of the signal, can change the result.

\paragraph{Models and tasks.} Three embedding models, five code-search sets and two BEIR sets. The
code-search results are exploratory for our system. Before this study, its production defaults (stage-1
size, graph pruning, early stopping) were tuned on gcsn queries, including queries that are held-out
here, with the earlier speed ratio against rivals as an acceptance check; dev and held-out code queries
also share most source repositories (the bootstrap resamples repositories, which accounts for this
inside a set but not across sets). The BEIR sets were not used in that tuning. The confirmatory part is
the \nm{nconfirm} primary comparisons on Quora and FiQA with enough power.

\paragraph{Machines.} Every Linux machine is a virtual machine, so page sizes, frequency and
neighbour load are not under our control. A/A runs measured this noise per machine and set $R$; the
rounds of one point usually ran on different instances, so instance-to-instance variation is inside
the intervals. Results on bare metal can differ, in particular for the graph walks, whose cost depends
on TLB behaviour. The Mac runs unpinned. The box and the Mac run a reduced grid.

\paragraph{Single queries, single thread.} We time one query at a time on one core. Batched search,
multi-threaded search and shared-index throughput are out of scope; several rivals (FAISS flat
scans, IVF) gain more from batching than graph walks do. Our index build is single-threaded; the
rival builds used the thread counts in Table~\ref{tab:build}. Build cost is indicative only
(\S\ref{sec:systems}).

\paragraph{Tested interfaces.} Each rival is used through the interface we wrapped: the C++ API for
FAISS, hnswlib, USearch, DiskANN and SVS, and the Python binding for ScaNN. Another interface,
another build of the same library, or parameters outside the declared grids can be faster. We
declared the grids before the dev runs and widened two (IVF probes and ScaNN leaves) on dev, before
the freeze, when those families did not reach the fractions.

\paragraph{Our harness.} Our system runs in Node.js with a native addon, the rivals in C++ (ScaNN in
Python). Comparison (A) runs our generators through the addon and the shared steps in both C++ and the
addon with bit-identical lists, so the generator times include the language boundary of each system.

\paragraph{Sources of variance.} Rounds of one point ran on different instances of the same type, so
instance-to-instance variation is inside the intervals, but we did not separate it, and every index
was built once (seed 42): variation between independent builds of the same configuration is not
measured. Build cost comes from the builds that produced the timed indexes, which ran concurrently,
not from isolated build runs.

\paragraph{Secondary platforms.} The box and the Mac reuse the operating points of the AMD and
Graviton types and run a smaller set of rivals (no ScaNN, DiskANN or SVS on the Mac), so their
geometric means are not comparable with those of the AWS CPUs.

\paragraph{Missing analyses.} Native-only timing, the shipped default and stage clocks ran only after the
freeze (\S\ref{sec:post}); tail latencies and recall@10 are computed from the held-out records
(\S\ref{sec:results}). The plan also asked for variation between independent builds, isolated build-cost
runs, the first 100 cold queries, the memory split into anonymous and file-backed pages with the
huge-page backing, and dTLB counters; these did not run.

\paragraph{Rival configurations.} The refining rivals rescore with float32 originals; ours uses float16
vectors. A float16 refine for FAISS and a rescoring USearch int8 variant exist in the libraries but were
not in the grid. Each index was built once, with one seed.

\paragraph{The reporting scripts.} The reporting scripts (\texttt{analyze.py}, \texttt{merge\_results.py},
\texttt{paperlib.py}, \texttt{mem\_patch.py}, \texttt{mktex.py}, \texttt{figures.py}) were written after
the freeze, and two of their rules changed after the held-out results were seen (the ratio statistic
and the choice of the headline rival; Appendix~\ref{app:deviations}). They call the frozen quality and
statistics code; we release them with the data so that every table can be checked against the raw
records. The freeze record covers the harness, plans and set definitions, but also files unrelated to
this study, and it does not hold binary hashes; those are in each machine's build record.
