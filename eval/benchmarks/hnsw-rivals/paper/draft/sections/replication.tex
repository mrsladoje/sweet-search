\section{Pre-registered replication on untouched sets}\label{sec:replication}

The main study is exploratory (\S\ref{sec:protocol}, Appendix~\ref{app:deviations}). To test its speed pattern once, we
ran a replication on two sets that no earlier step used, with a corrected harness and rules written before any
replication data existed. The plan, \texttt{REPLICATION\_PLAN.md}, was committed at \texttt{6e4f9c42} (2026-10-19, 00:06
CEST) together with the analysis scripts; two independent pre-run reviews were applied to it before the first timing run
(\texttt{804439f0}), and the git history records every change. The dev selections and held-out plans were frozen with
file hashes in \texttt{REPFREEZE.json} before any held-out job of the CPU type ran (\texttt{74e8c4b5} for AMD,
\texttt{4740606a} for Intel and Graviton). The held-out analysis (\texttt{rep\_analyze.py}) ran once, unchanged.

\subsection{Design}

\paragraph{Sets.} \emph{CQADupStack}: all 12 BEIR forums merged into one corpus of 457,199 documents (ids prefixed by
forum, relevance only within a forum), 13,145 queries split 60/40 (seed 42) \emph{within each forum}, so both splits hold
every forum: 7,887 dev and 5,258 held-out queries. \emph{MS MARCO 1M}: every passage judged for any of the 6,980 BEIR dev
queries (7,433 passages), plus a seeded uniform sample (Fisher--Yates, seed 42, over the sorted ids) of the other
8,834,390 passages, 1,000,000 passages in all; the 6,980 queries split 4,188 dev and 2,792 held-out. One vector per
document, embedded with bge-base-en-v1.5 (pinned revision); $k_v = 10$ on both sets. The plan applies the self-match rule
of Quora to any query id that is also a corpus id. MS MARCO query and passage ids share one number range, so for 814 of
the 6,980 queries the rule removed the passage whose id equals the query id, for every system and for exact search; none
of these passages is relevant to its query, but the rule was meant for Quora and has no purpose here.

\paragraph{Systems.} Ours: the production cascade (scan up to 150k vectors, walk above, so the walk runs on both sets),
production build, only at stage-1 sizes the product itself runs (no bench-only override). Rivals: every family of the
main study that runs on the CPU, one build each (the build most often frozen for that family in the main study), and
every effort knob (ef, DiskANN $L$, SVS window) on the same 11-value grid as our stage-1 size, from 50 to 3,000. No build
tuning on these sets for any system.

\paragraph{Harness corrections.} Rival timers compute only the query forms the family uses; each job pre-reads only the
files it opens; each plan file holds every system of one (set, round) and runs on one instance, in a seeded random order;
and a job with more than 1,000 major page faults in its timed pass runs once more and is invalid if the rerun also exceeds
1,000, in which case its block is dropped. The rule applies to every system alike.

\paragraph{Selection and tests.} On dev, at $\fr = 0.99$, each system's point is its fastest configuration whose
one-sided 97.5\% cluster-bootstrap bound of mean($Q_{\text{sys}} - 0.99\,Q_{\text{exact}}$) is at least 0, with latency the
median of three dev rounds; the rival of each test is the rival fastest on dev. Held-out: each CPU type ran 6 fresh
instances, each with 2 blocks. The latency test is a one-sided $t$-test (5 degrees of freedom) over the 6 instance means
of log(rival / ours). The quality test is non-inferiority with a relative margin: $H_0$: mean($Q_{\text{ours}} -
Q_{\text{rival}} + 0.005\,Q_{\text{exact}}) \le 0$, one-sided at 0.025, bootstrapped jointly over queries. Each family of 6
tests is Holm-corrected at 0.025. A set--CPU pair counts as ``faster and not worse'' only if both tests pass. This joint
claim is relative to the rival; whether a system keeps 99\% of exact quality is a separate, descriptive question.

\subsection{Results}

\paragraph{Latency.} Table~\ref{tab:rep} gives the six pre-registered latency tests. All \nm{rep-lat-pass} pass after Holm;
the geometric mean ratio over instances is \nm{rep-gm} (from \nm{rep-min} to \nm{rep-max}). At the 99th percentile the
ratio is \nm{rep-p99}, so in the replication our tail is also shorter than the rival's. Our native calls take
\nm{rep-native}\% of our timed query (median); the rest is JavaScript and metadata reads.

\paragraph{The fault rule.} Every job that exceeded the fault limit was ours, on MS MARCO, where our memory-mapped files
are largest: \nm{rep-reruns-w} timed jobs (and four native-clock jobs) ran again and passed on the rerun; \nm{rep-dropped-w}
block was dropped (\nm{rep-sens-cell}, block 3: \nm{rep-sens-f1} and then \nm{rep-sens-f2} major faults in our timed
pass). With that block put back, the AMD MS MARCO ratio falls to \nm{rep-sens-ratio} and the one-sided $p$ rises to
\nm{rep-sens-p}, which would not pass. So that one pass depends on the pre-registered rule, which treats a job whose
index was read from disk during timing as invalid for every system alike. Its result describes a server whose index stays
in the page cache; \S\ref{sec:losses} discusses the other case.

\paragraph{Quality.} Table~\ref{tab:rep-q} separates three questions. \emph{Non-inferiority to the rival} (the
pre-registered test) passes on MS MARCO on all three CPUs and fails on CQADupStack on all three: there the mean
difference to the rival is between $-0.0010$ and $0.0000$ nDCG@10, but its lower bound falls just below the margin of
0.0021. \emph{Retention against exact search} (descriptive): on MS MARCO our point keeps \nm{rep-share-ours-msm} of exact
quality, with a bound of \nm{rep-share-ours-msm-lo}, so it meets 99\% by the bound; on CQADupStack it keeps
\nm{rep-share-ours-cqa} by the point estimate, with a bound of \nm{rep-share-ours-cqa-lo}, so it does not meet 99\% by the
bound, and neither does any of the three rivals. \emph{The joint claim} (faster and not worse than the rival by more than
0.5\% of exact quality) holds in \nm{rep-joint} of \nm{rep-n} pairs, all on MS MARCO. On CQADupStack the speed advantage is
shown, but at a retained quality that is not established at 99\%.
