\section{Introduction}\label{sec:intro}

Dense retrieval for code search and question answering often runs on one CPU core, next to the application, over a
corpus of thousands to about a million vectors. At this size every design is practical: an exact scan, a quantised
flat scan, a graph or a partition index. Benchmarks such as ANN-Benchmarks~\cite{aumuller2020annbenchmarks} rank these
designs by recall against the exact neighbours. A deployed system, however, rescores the candidates and maps vectors to
documents, and its users see the task quality of the final ranking. Recent work argues that neighbour recall can
mislead about that quality~\cite{chen2026iceberg,dimitropoulos2026recall}.

We ask: \emph{at a fixed fraction of the task quality of exact search, which index answers a single query fastest on a
CPU, and how does the answer change with corpus size and CPU?} The system under test is the binary cascade of the \sweet
code-search tool~\cite{sweetsearch_repo}: a 512-bit sign code of each vector, an HNSW graph on the codes or an exact scan
of them, an int8 screen and float16 rescoring. The method is not new (\S\ref{sec:related}); the question is how fast a
careful implementation of it is against the main CPU libraries when all of them are held to the same task quality. The
tool is ours, so we treat the study as a test of our own design and fix its rules in advance.

\paragraph{Three stages.} The paper reports three stages, in this order of evidential weight. (1) A
\emph{pre-registered replication} (\S\ref{sec:replication}) on two sets that no earlier step used, with a corrected
harness, six fresh instances per CPU type and one held-out look; it holds the paper's only confirmatory latency tests.
(2) An \emph{exploratory main study} (\S\ref{sec:protocol}--\S\ref{sec:results}) on seven sets, three models and five
CPUs, with dev-only selection and a hashed freeze, but with flaws found after the freeze (Appendix~\ref{app:deviations}).
(3) \emph{Post-freeze diagnostics} (\S\ref{sec:post}) that isolate generator time and explain slow rounds.

\paragraph{Contributions.}
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{A protocol for ANN comparisons at fixed task quality.} Each system runs at the fastest configuration that
keeps a fraction $\fr$ of exact-search MRR@10 or nDCG@10, chosen on dev queries with a cluster-bootstrap bound and frozen,
with file hashes, before held-out queries run; repeated rounds sized by A/A runs; and a pre-registered replication with
the instance as the unit. The replication plan and its analysis code were public
on GitHub five hours before its first timing job. To our knowledge, pre-registration is rare in ANN benchmarking.
\item \textbf{Recall against task quality.} On the code sets, \nm{rec-dist-low} of our \nm{rec-dist-n} distinct operating
points have recall@10 between \nm{rec-dist-min} and 0.9, also at document level, and still keep 99\% of exact task
quality; on the two replication sets no configuration that keeps 99\% falls below recall@10 = 0.9, but a recall target
still misorders configurations in both directions (\S\ref{sec:results}).
\item \textbf{A map of candidate generators} behind one shared rescoring procedure, from 7k to 1M vectors on five CPUs
(\S\ref{sec:results}), and an equal-settings comparison of binary HNSW implementations on the same codes: our walk is
\nm{post-eqb-min}--\nm{post-eqb-max} times faster than FAISS and USearch binary HNSW (\S\ref{sec:post}).
\item \textbf{A confirmatory speed result}: in the replication our cascade was faster than the rival chosen on dev in
\nm{rep-lat-pass} of \nm{rep-n} pre-registered tests, one of them only under the pre-registered page-fault rule; quality
non-inferiority held on MS MARCO and not on CQADupStack
(\S\ref{sec:replication}).
\item \textbf{Where the cascade loses}, in the main text (\S\ref{sec:losses}), and the harness, frozen points and every
record for others to check the results and add systems (\S\ref{sec:repro}).
\end{itemize}

We do not claim the fastest ANN method or equal quality. Every result holds for the tested sets, models and CPUs, within
the declared quality margin. Results on the code sets are exploratory, because our production defaults were tuned
earlier on the same code queries.
