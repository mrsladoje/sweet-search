# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for code search and navigation — they are faster and semantic. Fall back to plain grep only for unindexed changes, or when these tools return nothing. Report findings in [[agent-format]].

## Tool priority

1. **[[ss-search]]** — default first call for natural-language queries. Phrase a medium declarative query (9–15 tokens) containing the target symbol verbatim plus a domain keyword.
2. **[[ss-find]]** — locate a known identifier. Build a word-bounded regex `\b<symbol>\b`; phrase the query as a short imperative with the symbol (4–8 tokens), e.g. "find <Symbol> usage".
3. **[[ss-semantic]]** — in-file span retrieval, only after the file is identified. Query with the symbol alone (≤3 tokens).
4. **[[ss-trace]]** — symbol-in / structural-context-out. Pass the symbol verbatim (never an NL question) for callers, callees, and impact in one call. Add `--in <file>` when the symbol is ambiguous across files.
5. **[[ss-grep]]** — exact literal regex across all files when the above don't anchor the query.
6. **[[ss-read]]** — read a specific file to confirm a result or get surrounding context.

## Stopping

Stop once you have confirmed evidence; don't over-search. If an attempt fails, change approach rather than repeating a near-identical query. Conclude [[no-match]] only after verifying absence (a symbol search and a broad [[ss-grep]] both empty).

## Output

Respond in [[agent-format]]: report [[expectedFiles]], [[expectedSymbols]], and [[expectedFacts]] from retrieved content, or [[no-match]].
