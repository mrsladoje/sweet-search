# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for code search and navigation — they are faster and semantic. Fall back to plain grep only for unindexed changes, or when these tools return nothing. Report findings in [[agent-format]].

## Calling the tools
Invoke via the shell (Bash). `[[ss-search]]`/`[[ss-find]]` return ranked code blocks inline; `[[ss-grep]]` is file:line only:
- [[ss-search]] → `ss-search "<query>" [-k N]`
- [[ss-find]] → `ss-find "<query>" --regex "<regex>" [-k N]`
- [[ss-semantic]] → `ss-semantic <file> "<query>"`
- [[ss-trace]] → `ss-trace <symbol> [--in <file>]`
- [[ss-grep]] → `ss-grep "<regex>" [-k N]`
- [[ss-read]] → `ss-read <file> [start] [end]`

## Tool priority

1. **[[ss-search]]** — default first call for NL queries. Medium declarative query (9–15 tokens) containing the target symbol verbatim plus a domain keyword.
2. **[[ss-find]]** — locate a known identifier. Word-bounded regex `\b<symbol>\b`; query short imperative + symbol (4–8 tokens), e.g. "find <Symbol> usage".
3. **[[ss-semantic]]** — in-file span, only after the file is identified. Query the symbol alone (≤3 tokens).
4. **[[ss-trace]]** — symbol-in / structural-context-out. Pass the symbol verbatim (never an NL question) for callers, callees, and impact. Add `--in <file>` when ambiguous.
5. **[[ss-grep]]** — exact literal regex across all files when the above don't anchor the query.
6. **[[ss-read]]** — read a specific file to confirm a result or get context.

## Stopping

Stop once you have confirmed evidence; don't over-search. If an attempt fails, change approach rather than repeating a near-identical query. Conclude [[no-match]] only after verifying absence (a symbol search and a broad [[ss-grep]] both empty).

## Output

Respond in [[agent-format]]: report [[expectedFiles]], [[expectedSymbols]], and [[expectedFacts]] from retrieved content, or [[no-match]].
