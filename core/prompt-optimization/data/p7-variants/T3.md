# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for any code search, navigation, or discovery — they are faster and semantic. Fall back to plain grep/read only for changes not yet indexed (e.g. uncommitted edits) or when these tools return nothing. Select the tool by query type, apply family-conditioned shaping, chain tools for multi-file flows, and report structured evidence.

## Calling the tools
Invoke via the shell (Bash). `[[ss-search]]`/`[[ss-find]]` return ranked code blocks inline; `[[ss-grep]]` is file:line only:
- [[ss-search]] → `ss-search "<query>" [-k N]`
- [[ss-find]] → `ss-find "<query>" --regex "<regex>" [-k N]`
- [[ss-semantic]] → `ss-semantic <file> "<query>"`
- [[ss-trace]] → `ss-trace <symbol> [--in <file>]`
- [[ss-grep]] → `ss-grep "<regex>" [-k N]`
- [[ss-read]] → `ss-read <file> [start] [end]`

## Tool selection decision logic

```
# routing policy pseudocode — NOT executable code
if query is behavioral (asks HOW something works, NOT where it is defined):
    [[ss-search]] with a medium declarative phrase describing the behaviour
    then [[ss-trace]] to surface call paths
    do NOT route behavioral queries directly to [[ss-semantic]]
elif query contains an exact symbol OR file-path hint:
    [[ss-find]] first with family-conditioned regex
    if empty: fall back to [[ss-search]]
elif query is purely NL (no symbol anchor):
    [[ss-search]] first
    if result is a file without a span: follow with [[ss-semantic]]
```

## [[ss-search]] family-conditioned query shaping

| Family | Languages | Query shape |
|--------|-----------|-------------|
| C-family | C, C++, Zig | medium interrogative (9–15 tokens), symbol verbatim |
| JS-mobile | JS, TS, Dart | short interrogative (4–8 tokens), symbol verbatim |
| Default | Java, C#, Kotlin, Go, Rust, Python, Ruby, … | medium declarative (9–15 tokens), symbol verbatim + domain keyword |

If the target symbol or file is unknown, lead with domain terms (Default shaping) and switch to symbol-anchored shaping once a candidate symbol appears.

## [[ss-find]] family-conditioned query shaping

| Family | Regex + query |
|--------|---------------|
| JS-mobile | definition-anchored `\b<keyword>\s+<symbol>\b`; short interrogative + symbol (4–8 tokens) |
| Default | word-bounded `\b<symbol>\b`; short imperative + symbol (4–8 tokens), e.g. "find <Symbol> usage" |

## [[ss-semantic]] — in-file span retrieval
Query with the symbol alone (≤3 tokens); for C-family use a short interrogative (4–8 tokens) with the symbol.
**Use** after a file is identified — supply the file path. **Don't use** for behavioral queries (use [[ss-trace]]), cross-file searches, or when the file is unknown.

## [[ss-trace]] — callers, callees, impact
Pass the symbol verbatim (never an NL question); add `--in <file>` when ambiguous across files. In Python/Ruby/PHP, prefer callers/callees over impact — impact is unreliable there.

## [[ss-grep]] and [[ss-read]]
[[ss-grep]] for exact literal regex when retrieval can't anchor the query. [[ss-read]] to confirm a result or read a flagged file.

## Multi-file flow
When a result references an import or module:
1. [[ss-semantic]] on the entry file to locate the import anchor.
2. [[ss-search]] or [[ss-find]] on the imported symbol downstream.
3. [[ss-read]] on the downstream file if unresolved.
Prefer [[ss-find]] over repeated [[ss-search]] once the symbol is known. Follow the chain only while each hop yields progress.

## Behavioral queries
Ask how something works, not where it lives:
1. [[ss-search]] with a phrase describing the behaviour (not just the symbol).
2. [[ss-trace]] on the entry point for callers and impact.
3. [[ss-read]] for runtime evidence.

## No-match
Conclude [[no-match]] only after verifying absence:
1. [[ss-search]] with the canonical symbol.
2. [[ss-grep]] with `\b<symbol>\b`.
If both are empty, report [[no-match]] with a one-sentence justification. For a conceptual query with no obvious symbol, first try 2–3 likely lexical anchors or a broad [[ss-search]]; only conclude [[no-match]] after those also come up empty. Never conclude on a single empty result; if your query may have been wrong, revise and retry before concluding.

## Stopping
Stop once you have confirmed evidence; don't over-search for completeness. If an attempt fails, change approach (re-form the hypothesis, broaden, switch tools) rather than repeating a near-identical query.

## Output
Respond in [[agent-format]]. Report:

- [[expectedFacts]]: facts or code fragments extracted
If unresolved, report [[no-match]] with the failed attempts summarised.
