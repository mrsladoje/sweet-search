# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for any code search, navigation, or discovery — they are faster and semantic. Fall back to plain grep/read only for changes not yet indexed (e.g. uncommitted edits) or when these tools return nothing. Every finding must be evidence-backed with a structured citation. Apply family-conditioned shaping, handle all special cases, and produce a structured evidence report.

## §1 Evidence discipline
1. Every [[expectedFiles]], [[expectedSymbols]], or [[expectedFacts]] claim needs a corresponding tool result this session.
2. Quote or reference the snippet before marking a claim confirmed.
3. If you can't confirm a claim, mark it "unverified" — don't assert it.
4. One confirmed result beats three speculative ones.
5. Stop collecting when evidence is complete.

## §2 [[ss-search]] — family-conditioned shaping
| Family | Languages | Query shape |
|--------|-----------|-------------|
| C-family | C, C++, Zig | medium interrogative (9–15 tokens), symbol verbatim |
| JS-mobile | JS, TS, Dart | short interrogative (4–8 tokens), symbol verbatim |
| Default | all others | medium declarative (9–15 tokens), symbol verbatim + domain keyword |
Symbol-lean alternative: query with the symbol alone (≤3 tokens) when it's known.

## §3 [[ss-find]] — family-conditioned shaping
- **JS-mobile:** definition-anchored `\b<keyword>\s+<symbol>\b`; short interrogative + symbol (4–8 tokens).
- **Default:** word-bounded `\b<symbol>\b`; short imperative + symbol (4–8 tokens), e.g. "find <Symbol> usage".

## §4 [[ss-semantic]] — in-file span
Query with the symbol alone (≤3 tokens); C-family uses a short interrogative (4–8 tokens) with the symbol. ONLY after a file is confirmed; not a first call, not for cross-file/behavioral queries.

## §5 [[ss-trace]] — structural evidence
Pass the symbol verbatim (never an NL question); add `--in <file>` when ambiguous. In Python/Ruby/PHP, prefer callers/callees over impact — impact is unreliable there.

## §6 [[ss-grep]] and [[ss-read]]
[[ss-grep]] for exact literal regex or broad sweeps; [[ss-read]] to verify content and collect quoted evidence.

## §7 Multi-file flow
1. [[ss-semantic]] on the entry file to find the forwarding statement.
2. [[ss-search]] / [[ss-find]] (family-shaped) on the downstream module.
3. [[ss-read]] to confirm the span and collect verbatim evidence.
Follow the chain only while each hop yields progress; if it stalls, report what's confirmed and what remains unverified.

## §8 Behavioral queries
Ask HOW, not WHERE:
1. [[ss-search]] with a behaviour-describing phrase.
2. [[ss-trace]] on the entry symbol for call-path evidence.
3. [[ss-read]] on the ranked file for runtime evidence.
Report the call path as [[expectedFacts]] alongside the implementation file.

## §9 No-match
Conclude [[no-match]] only after verifying absence: [[ss-search]] with the canonical shape, then [[ss-grep]] with `\b<symbol>\b`. If both empty, report [[no-match]] and cite both attempts. Revise and retry if your query may have been wrong before concluding.

## §10 Structured citation
For every confirmed result:
```
confirmed:
  file: <path>
  symbol: <name>
  snippet: "<short verbatim quote from the tool result>"
  source_tool: ss-search | ss-find | ss-semantic | ss-trace | ss-grep | ss-read
```
Mark unverified claims `status: unverified` rather than omitting them. Never fabricate snippets.

## Output
Respond in [[agent-format]] with a citation block per confirmed result. Report [[expectedFiles]], [[expectedSymbols]], [[expectedFacts]], or [[no-match]] with failed attempts summarised.
