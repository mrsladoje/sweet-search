# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for any code search, navigation, or discovery — they are faster and semantic. Fall back to plain grep/read only for changes not yet indexed (e.g. uncommitted edits) or when these tools return nothing. Verify absence before asserting a result, and confirm negatives efficiently for queries that imply something may not exist.

## No-match-first protocol
For queries that may legitimately return nothing — "does X exist", "is there a Y", or a symbol that may have been removed or renamed — verify absence first:
1. [[ss-grep]] with `\b<symbol>\b` — literal word-bounded sweep.
2. If empty, [[ss-search]] with the symbol as a short imperative query.
3. If both are empty AND the symbol spelling is certain, report [[no-match]] with both summaries. If the name might be wrong or aliased, try a variant before concluding.
4. If either returns a result, continue with the full flow below.

## Full routing flow
### [[ss-search]]
Medium declarative query (9–15 tokens) containing the symbol verbatim plus a domain keyword.
### [[ss-find]]
Word-bounded regex `\b<symbol>\b`; query short imperative + symbol (4–8 tokens), e.g. "find <Symbol> usage".
### [[ss-semantic]]
Query with the symbol alone (≤3 tokens); only after a file is confirmed.
### [[ss-trace]]
Pass the symbol verbatim (never an NL question) for callers, callees, and impact; add `--in <file>` when ambiguous. In Python/Ruby/PHP, prefer callers/callees over impact — impact is unreliable there.
### [[ss-grep]] and [[ss-read]]
[[ss-grep]] for literal patterns and broad sweeps; [[ss-read]] to confirm a file.

## Stateful summary rule
Before your 3rd tool call (or before your final answer, whichever comes first), you MUST output a `<state_summary>` block containing exactly: (1) one sentence summarising what you've established so far, (2) one sentence stating your current blind spot or open question.
