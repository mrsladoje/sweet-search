# Sweet-search — code search tool guide

Sweet-search provides index-backed code search tools. Prefer them over raw grep/ripgrep and blind file reads for code search and navigation — they are faster and semantic. Fall back to plain grep only for unindexed changes, or when these tools return nothing. Evidence discipline is your primary rule: never report a result you have not confirmed with a tool call. Retrieve; verify; report.

## Calling the tools
Invoke via the shell (Bash). `[[ss-search]]`/`[[ss-find]]` return ranked code blocks inline; `[[ss-grep]]` is file:line only:
- [[ss-search]] → `ss-search "<query>" [-k N]`
- [[ss-find]] → `ss-find "<query>" --regex "<regex>" [-k N]`
- [[ss-semantic]] → `ss-semantic <file> "<query>"`
- [[ss-trace]] → `ss-trace <symbol> [--in <file>]`
- [[ss-grep]] → `ss-grep "<regex>" [-k N]`
- [[ss-read]] → `ss-read <file> [start] [end]`

## Evidence rules
1. Never assert a file path, symbol, or fact from prior knowledge — every claim must be backed by a tool result.
2. Read the snippet to confirm it contains the expected content before reporting.
3. Prefer a shorter, confirmed answer over a long, speculative one.

## Tool sequence
1. **[[ss-search]]** — natural-language query; rephrase once if the first attempt is empty.
2. **[[ss-find]]** — regex `\b<symbol>\b` when the symbol is known.
3. **[[ss-semantic]]** — in-file span, only after a file is confirmed by step 1 or 2.
4. **[[ss-trace]]** — callers/callees/impact, only with a confirmed symbol.
5. **[[ss-grep]]** — literal pattern fallback across all files.
6. **[[ss-read]]** — direct file read for verification.

## Stopping
Stop once evidence is verified — no extra calls. If an attempt fails, change approach, don't repeat a near-identical query. Conclude [[no-match]] only after a symbol search and a broad [[ss-grep]] both come up empty.

## Output
State a file, symbol, or fact only when it is backed by a specific tool result, or [[no-match]].
