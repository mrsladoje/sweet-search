# TRIED-LEVERS — every product, prompt and tool-output lever tried before (as of 2026-10-01)

This file stops us from re-running dead experiments. A new variant that matches a row below is not new. It counts as new only when its mechanism differs in a stated, concrete way.
The sweep read the memory notes, the handoff folders and the git log. It did not re-measure anything. Numbers are copied from the sources and carry their sign.

## How to read this file

- **Status words.** SHIPPED = in production. DEAD = killed at a gate or by a live test. REFUTED = a test showed the opposite of the claim. REVERTED = shipped or built, then taken out. SUPERSEDED = was a bench champion, replaced before it reached a release. OPEN = never decided or never run. "Default OFF" = code exists, switch is off.
- **Evidence column.** `MEM:` = file in `/Users/admin/.claude/projects/-Users-admin-Projects-sweet-search-private/memory/`. `HO:` = `eval/task-completion-bench/handoffs/` in the private repo. `REG:` = row id in `HO:improve/slate-c/register/DEAD-LEVER-REGISTER.md` (123 rows, written 2026-09-02). Bare hashes are commits in the private repo.
- **Backbone warning.** Most task-bench evidence used gpt-5.6-luna (cheap OpenAI-family model) in Codex, opencode and Claude Code, plus Grok-4.5 in opencode (July to August 2026). The June 2026 budget sweep used DeepSeek-V4-Pro, MiMo-2.5-Pro, GPT-5.5 and Opus-4.8. The r282 cells (Sonnet 5.5, Opus 5.5, GPT-6.1 Sol, DeepSeek V4.1 Flash) were never used to test any lever below. A replay or a luna result does not give the size of the effect on those cells. The sources say this themselves: a replay gets the direction right about half the time and the size never.
- **Noise facts that decide what can be tested.** Per-task cost log-SD: Codex 0.198, opencode 0.185, Claude Code 0.160. Minimum detectable effect (80% power): 1 cell 29-57%, 2 cells 22-28%, 4 cells 15-19%, 8 cells 10.5-13% (MEM: project_harness_hillclimb_result; HILLCLIMB.md "noise floor"). Earlier turn-fix work measured aggregate cost noise of plus or minus 37% at n=19 (MEM: project_turnfix_program).
- **Corrections to the task brief and the memory notes** (details in the section "Source conflicts and gaps"): the hash 53ad493 is not on main (main has the same change as 2c175a8e); the Codex, opencode and Claude Code variants in release 2.8.2 are NOT the ones named in the brief (pallyt and todoall never reached a release; max-batch shipped on 2026-09-26 and was replaced); the memory phrase "gutter is a validated minus 16% lever" came from a small micro-smoke and was later withdrawn.

## Implications for final tuning (2026-10-01)

**Conclusion:** All seven ideas are still open at the mechanism level on the r282 cells. Three (a, e, f) have close relatives that failed. Two (c, d) were never tested live. Two (b, g) have a small ceiling.

### (a) Rank-shaped ss-search output: partly tried, the exact shape is open

- The product is already rank-shaped. By `allocateBudget` (`core/search/context-expander.js`, lines 47 and 1467-1530): rank 1 is full (cap 2,000 tokens, 60% of the budget), ranks 2-3 are previews (caps 800 and 400 tokens, 20% each), rank 4 and lower are summaries with no code. The new idea only changes ranks 2-3.
- Closest equivalent: row 1.8 (pointer tail). It turned rank 2-3 bodies into bare `file:line` pointers. Result: solves 3/8 v 5/8 on read-heavy tasks, then 4/12 v 4/12 on fresh tasks, no cost win. It fired only when top-1 scored 3x the lower rank, so it was a weak test. A trace review found 1 of 4 costly tasks would be hurt (rank 2 was load-bearing).
- Usage data (row 1.9, luna, Claude Code): rank 2 and rank 3 are used later 35.1% and 31.4% of the time. That is above the 20% kill line of the parked lever B13. Ranks 4-5 are only 2% of pack bytes each. Edited files first appeared at rank 6 or lower in 20.6% of cases (row 1.10), so the path list must stay.
- The flat budget cuts (rows 1.5, 1.6) do not test this. By the code, at 2k the rank-1 cap drops from 1,800 to 1,200 tokens while rank 3 stays at 400. This is my reading of the code, not a measurement. Opus may have compensated for a cut rank 1, not for cut ranks 2-3.
- **A new variant must differ in these ways.** Keep the rank-1 cap independent of the total budget. Replace ranks 2-3 with path, symbol, signature, line range and the exact `ss-read` command (not a bare `file:line`). Do not gate on score dominance. Read calls, `ss-read` follow-ups on rank-2/3 files and delivered tokens as the mechanism metrics. Test on Opus/Claude Code first, because Opus bought back cut context with calls. Use the break-priced cost column.

### (b) Metadata trim in ss-search output: partly tried, the core is unmeasured

- Already done: the route trailer became one line (row 1.20, no A/B); the trailer diet (row 1.22); unread-above printing only on a signal (row 1.17); gutters settled (rows 1.23-1.26).
- The density pass (row 1.21) is a different class. It reformats code lines and is banned by `BRIEF.md` rule 7. It measured 1.9% after keeping doc comments.
- Never measured: the share of header line, `# confidence=` line, `score=`, presentation tags (`(preview kind=...)`) and the route trailer. By the wrapper code (`_ss-helpers.mjs` lines 905-917 and `search-format.js`), the route trailer repeats `confidence` and `sufficient` from the header. My rough estimate is 120-150 tokens per call, 5-8% of a call. This is an estimate to be replaced by the §2.5 measurement.
- ss-* payload is 18.95% of Claude Code sweet cost (luna). A 10% payload cut is under 2% of cost. That is below the r282 noise floor, so test it by mechanism metrics.
- **A new variant must differ in these ways.** Remove only lines that cannot change the next action. Keep `sufficient=` and `same file:` because the rules text depends on them (rows 4.9, 1.19). Leave gutters alone (REG C3-C7 are settled; do not delete the gutter). Measure the metadata share first. Watch for Opus compensation in calls.

### (c) Remove ss-semantic, ss-find and ss-trace: never tested live

- Only $0 estimates exist (row 3.2). Call share: 11.4% of ss-* calls on luna (ss-find 8.3, ss-semantic 1.9, ss-trace 1.2) and about 19% on the Sol r282 cell. Guide lines for these tools: 133-164 tokens of the paragraph-level trim, -0.24% to -0.5% per harness. My count: 8 lines of the guide name these tools (2,212 of 6,006 body characters), so a proper rewrite could save roughly 200-300 tokens. That is an estimate.
- The one candidate (c04) died because it bundled the fix-surface paragraph, which is a shipped lever (row 4.10). The ss-semantic part alone passed its kill test.
- Related failures: ss-trace as the spine of multi-file search (+65%, row 2.11); the prompt-level tool mask (row 3.3); `ss-batch` (row 3.1).
- Coupling to handle: the fix-surface paragraph names `ss-trace` (with `ss-grep` as the alternative); the exact-token bullet names `ss-find`; `init --mcp` exposes search and trace; the owner protected the guide's guidance block on 2026-08-10 and 2026-08-13 and banned new tools on 2026-08-14.
- **A new variant must differ in these ways.** Run a live ablation (first ss-semantic alone, then the trio) with the rules text rewritten to match and no other change. Measure native fallbacks (Claude Code sweet arm already uses native tools at times) and miss chains. Do not count the shrink in guide tokens as the win; it is too small. Merge ideas (for example ranking inside `ss-grep`) are untested and need an owner decision.

### (d) Cache-stable prefix: not tested at mechanism level

- Closest: rows 4.31 and 4.32. Both closed on luna via OpenRouter by replay: Codex already cached 66% of turn-1 tokens; opencode and Claude Code 0.0%; best case 1.19%. The diagnostic "why is turn-1 caching 0% on Claude Code and opencode" was never run.
- r282 says cost is decided by caching: Opus naive input -2% but billed +22%; DeepSeek naive +5% but billed +55% (r282-RESULTS.md). The hypothesis (more cache writes or less reuse in the sweet arm) is unverified.
- One fact that may matter: every r282 rollout runs in its own clone path. Any working directory text placed before the static sweet text breaks sharing across rollouts. This is a hypothesis from the harness notes (the Claude Code environment block holds the working directory). The Phase 1 prefix-stability check decides it.
- Already done and closed: rules placement inside the system prompt (row 4.28, parity); removing the git status snapshot in the conflict-only Claude Code product (row 4.25, expected about 0).
- **A new variant must differ in these ways.** First prove a miss: cache-write and uncached tokens per request position on the Anthropic and DeepSeek cells. Then move dynamic text (paths, dates, index status) behind the static rules text, or out of the agent file. Read the result on the break-priced column and with cache writes at 1.25x. Do not reuse the luna replay as evidence.

### (e) Shorter sweet rules with the same tools: a small ceiling, with failed relatives

- Redundancy trim: 23 tokens saved, 0.07% of spend (row 4.30). The guide is 4.1% of sweet ideal spend on luna; it may differ on the r282 cells. Real savings need deleting rules, which needs a per-rule ablation that was never run (REG B2).
- Compression hurts: terse, tabular and numbered stop rules failed three times (row 4.4). The GEPA pruner mutation shaved the 1.8% of cost that the prompt represents and won only by noise.
- Owner direction conflicts: 2026-07-29 "M++ is tuned; do not reopen" and P8 struck; 2026-08-10/13 guidance block protected. The 2026-09-30 handoff lists a shorter prompt as hypothesis 3. Confirm the handoff overrides these before building.
- **A new variant must differ in these ways.** Ablate rules one at a time (30 rules, about 40 tokens each), keep the prose stop rules whole, use at least 3 repetitions, and read prefix tokens as the mechanism metric. Expect a cost effect at or below 4%, under the minimum detectable effect for one cell.

### (f) Stop and sufficiency guidance: heavily tried, nothing new without a measured waste

- Tried: rows 4.3, 4.4, 4.5, 4.6, 4.8, 4.9, 5.1, 5.2, 1.19. Findings: the full prose no-match rule is load-bearing and is shipped; compressing or sharpening it backfires; a louder rule relocates the loop; the `sufficient=` trailer is mostly noise (modal value `confidence=low sufficient=YES`); "widen on low" is dead; mid-task imperatives are ignored on Grok-4.5; the match-judgment trust variant cost +10%.
- r282 is retrieval Q&A with no edits. Sweet already uses fewer calls on Opus (-19.9%). Cost there is set by caching, so a call-count lever has little room. The census "hit then sufficient, followed by more calls" (FINAL_TUNING §2.6) has not been run.
- **A new variant must differ in these ways.** Target a measured waste from that census. Write it as prose in the rules text, not as compressed text or a trailer. Use 3 or more repetitions (two-repetition screens crowned a clone in gen-3). Check accuracy on the OOD set, which is the set where sweet wins.

### (g) Lower default top-K: mostly tried by proxy, small ceiling

- Defaults today: `ss-search -k 5`, `ss-find -k 6`, `ss-grep -k 20`. So `ss-search` is already at 5.
- Tried by proxy: prompt seed C ("default `-k 5`, narrow reads", row 4.5, weak lever); the clamp replay (row 1.10, 20.6% of edited files first seen at rank 6 or lower); the pointer tail (row 1.8).
- Ceiling: ranks 4 and 5 are 2.0% of pack bytes each (row 1.9), because rank 4 and lower are already summaries. Going from 5 to 3 saves about 4% of pack bytes at most. The bytes sit in rank 6 and lower (23.6%), which come from `ss-grep` and `ss-find` packs with large `-k`. The table does not split tools (source ambiguity 9).
- **A new variant must differ in these ways.** Change the `ss-grep` (20) and `ss-find` (6) defaults or add a per-file cap, not `ss-search`. Keep the round-robin file diversity and `(+N more in this file)` (row 2.6). Measure how often the agent then raises `-k` itself (one r282 Opus capture shows `ss-search -k 5; ss-grep -k 10`). Edit-task evidence (row 1.10) may not transfer to retrieval Q&A.
