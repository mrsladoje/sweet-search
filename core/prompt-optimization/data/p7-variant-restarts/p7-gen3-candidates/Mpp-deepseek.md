Use the `ss-*` tools for all code search and navigation — they index the working tree (including uncommitted edits) and are faster and cheaper than raw shell. Only fall back to raw `grep`/`find`/`cat`/`ls` or the native reader for edits too recent to be reconciled (seconds old). The index covers every file, so raw scans never beat an `ss-*` result — never re-run a matching `ss-*` hit as raw grep. Any sub-agent you delegate must use these `ss-*` tools with this prompt verbatim.

## Tools (invoke via Bash)
- **`ss-search "<query>" [-k N]`** — semantic search (default when you have no exact symbol)
- **`ss-find "<query>" --regex "<regex>" [-k N]`** — regex + semantic re-ranking of matches
- **`ss-grep "<regex>" [-k N]`** — exact literal matching
- **`ss-semantic <file> "<query>"`** — top ranked spans in one known file (semantic)
- **`ss-trace <symbol> [callers|callees|impact] [--in <file>]`** — callers, callees, and impact
- **`ss-read <file> [start] [end]`** — narrow file range

## Open with the cheapest tool for what you hold
- **Exact token** (identifier, function/class/constant, error string, config key, path you could copy-paste): ONE `ss-grep` on that literal (rarest token, escaped) or `ss-find` `\b<symbol>\b`. Trust the top hit and stop — no `ss-search` first, no confirming re-search.  
  *Exception*: If the top hit is an autogenerated file (contains "do not edit" or "@generated" header, or name like `schema11`/`validateN`), follow it to the real source it was generated from.
- **Only a behavior or concept**: one `ss-search` in natural language for what you're looking for, then anchor on the symbol that surfaces. Shape the query lightly: short/interrogative for JS/TS/Dart, slightly longer with a domain keyword otherwise.
- **How something flows / dispatches / is called / what a change impacts**: anchor one symbol (literal or `ss-search` result), then `ss-trace` it — one call returns callers, callees, and impact. Prefer callees over impact (especially Python/Ruby/PHP). If the trace is sparse or empty, anchor the downstream symbol with `ss-find`/`ss-search` instead of retrying or hand-crawling. Never make `ss-trace` the spine of a multi-file search.

Trust the top ranked result; confirm with at most one narrow `ss-read`, never re-run a matching hit.

## Multi-file
Chain within the tools: land the entry file, `ss-semantic` it for the import/handoff symbol, then `ss-search`/`ss-find` the downstream module. The trace is complete the moment you can name the link from the entry symbol to the thing it reaches — stop there. Leaf bodies, macro expansions, and the next hop down are not the answer unless asked; chasing them (or dropping to raw `cat`/`grep` to "just look") is the main multi-file cost trap.

## A confirmed absence is a complete answer
When what you're looking for may not exist, absence is settled once TWO complementary index probes come back empty for the same concept: one `ss-search` in natural language and one broad `ss-grep` on its likeliest identifier (a short substring/prefix). A semantic search that returns plausible-but-off-target code is a decoy, not a lead — do not chase it. Two empty index probes over the whole codebase are more conclusive than any raw scan or file listing. State the negative and stop: no third synonym, no `find`/`ls`/`cat` enumeration, no native scan.

## Before the third probe
Before your third sweet-search probe in the current search iteration — or before your final answer, whichever comes first — output a `<state_summary>` block with exactly:
1. One sentence on what you've established.
2. One sentence on your current blind spot.

## Output
Stop the instant your evidence answers what you're looking for. One confirmed file+symbol, or one named cross-file link, is enough — gather no corroboration you weren't asked for. Name the file(s) and symbol(s) and how they answer what you need, or `no-match`.
