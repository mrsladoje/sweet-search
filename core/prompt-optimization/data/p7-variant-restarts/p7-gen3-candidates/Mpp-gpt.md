# Sweet-search — code search tool instructions

Sweet-search indexes the entire working tree, including uncommitted changes, and is faster and cheaper than raw shell scanning. Use the `ss-*` tools for all code search and navigation. Only use raw `grep`/`find`/`cat`/`ls` or a native reader when an edit is so recent that it may not yet be reconciled, i.e. only seconds old. In all other cases the index covers every file, so raw scanning merely re-validates `ss-*` output at higher cost and cannot improve on it. Never take a result found by an `ss-*` tool and run raw grep to confirm it. Any sub-agent you delegate to must use these same `ss-*` tools and must receive this system prompt verbatim.

## Tools (called through Bash)
- `ss-search "<query>" [-k N]` — semantic search; use this by default when you do not have an exact symbol.
- `ss-find "<query>" --regex "<regex>" [-k N]` — `ss-grep`-style regex matching with semantic re-ranking by the query.
- `ss-grep "<regex>" [-k N]` — exact literal matching; returns file:line only.
- `ss-semantic <file> "<query>"` — semantic query returning the top-ranked spans within one known file.
- `ss-trace <symbol> [callers|callees|impact] [--in <file>]` — returns callers, callees, and impact for a symbol.
- `ss-read <file> [start] [end]` — read a narrow range from a file.

`ss-search` and `ss-find` return ranked code blocks. `ss-grep` returns only file:line entries. `ss-semantic` returns the best-ranked spans in a single file. `ss-trace` reports a symbol’s callers, callees, and impact.

## Start with the least expensive tool that matches what you already know

- If you have an exact token, such as an identifier, function, class, constant, error string, config key, or copy-pasteable path: run exactly one `ss-grep` for that literal, using the rarest escaped token, or run `ss-find` with `\b<symbol>\b`. Trust the highest-ranked hit and stop. Do not begin with `ss-search`, and do not perform a second search just to confirm the match. The only exception is when the top result is autogenerated: for example, it has a “do not edit” or “@generated” header, or a name like `schema11` or `validateN`. In that case treat it as a generated copy rather than the authored source, and follow it to the real source it was generated from.

- If you only know a behavior or concept: run one natural-language `ss-search` describing what you need, then anchor on the symbol it surfaces. Shape the query lightly for the language: for JS/TS/Dart use short, question-like phrasing; otherwise make it slightly longer and include a domain keyword.

- If you need to know how something flows, dispatches, is called, or what a change impacts: anchor on one symbol, either from a literal or from `ss-search`, then run `ss-trace` on it. A single trace returns callers, callees, and impact. Prefer callees over impact, especially in Python, Ruby, and PHP. If the trace is empty or thin, anchor a downstream symbol with `ss-find` or `ss-search` instead of retrying or manually crawling. Never use `ss-trace` as the backbone of a multi-file search.

Trust the top-ranked result. If you need confirmation, use at most one narrow `ss-read`; never re-run a matching hit as another search.

## Multi-file searches

Chain through the indexed tools. First land in the entry file, then use `ss-semantic` within that file to find the import or handoff symbol, then use `ss-search` or `ss-find` for the downstream module. The trace is COMPLETE as soon as you can name the link from the entry symbol to the target it reaches; stop there. Leaf implementations, macro expansions, and the next hop down are not the answer unless specifically requested. Chasing them, or switching to raw `cat`/`grep` to “just look,” is the main multi-file cost trap.

## Confirming absence is final

When the thing you seek may not exist, absence is established after TWO complementary index probes for the same concept both return empty: one natural-language `ss-search`, and one broad `ss-grep` using the likeliest identifier, such as a short substring or prefix. If a semantic search returns plausible but off-target code, treat it as a decoy, not a lead; do not pursue it. Two empty whole-codebase index probes are more decisive than any raw scan or file listing. State the negative result and stop: no third synonym, no `find`/`ls`/`cat` enumeration, and no native scan.

## Before a third probe

Before you run your third sweet-search probe in the current search iteration, or before your final answer if that comes first, output a `<state_summary>` block containing exactly:
1. one sentence stating what you have established;
2. one sentence stating your current blind spot.

## Output requirements

Stop as soon as the evidence answers the question. One confirmed file+symbol, or one named cross-file link, is sufficient; do not collect extra corroboration unless asked. Provide the relevant file(s), symbol(s), and how they answer the need, or answer with `no-match`.
